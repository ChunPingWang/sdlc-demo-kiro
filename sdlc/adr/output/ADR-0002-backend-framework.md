## 1. 背景與問題（Context）

需選定後端主要語言與應用框架，作為所有程式碼產出的基礎。

- 業務驅動：需與企業既有技術棧一致，便於人力調度與維運。
- 技術限制：須支援高並發保費試算請求。
- 前提假設：團隊具備 Java 與 Spring 生態經驗。

---

## 2. 決策（Decision）

> **我們決定：採用 Java 17 + Spring Boot 3.3。**

以 Spring Boot 3.3 為應用框架，Java 17 為語言基準（LTS），並可運用虛擬執行緒（Project Loom，Java 21 進一步強化）提升 I/O 密集場景的並發吞吐。

---

## 3. 考量的替代方案（Alternatives）

| 方案 | 優點 | 缺點 | 是否採用 |
|------|------|------|---------|
| **Java 17 / Spring Boot 3.3** | 企業技術標準、生態成熟、團隊熟悉、LTS | 記憶體占用較高 | ✅ 採用 |
| Node.js / NestJS | 開發快、非同步 I/O 佳 | 團隊經驗少、與企業標準不符 | ❌ 否決：不符企業技術標準 |
| Kotlin / Spring Boot | 語法精簡、與 Java 互通 | 團隊學習成本、招募池較小 | ❌ 否決：MVP 不引入額外學習成本 |

---

## 4. 結果與影響（Consequences）

**正面：**
- 與企業標準一致，人力可即戰。
- Spring 生態（Data JPA、Security、Springdoc）完整。

**負面 / 取捨：**
- 相較 Node 記憶體占用較高，需留意容器資源配置。

**後續行動：**
- 由 `java-coding-standards` Steering 規範 package 結構與分層職責。
